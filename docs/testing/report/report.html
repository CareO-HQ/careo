Setting up for manual testing

  1. Start the local stack: npx supabase start, then apply migrations with npx supabase db reset (or npx supabase migration up). Four migrations are new on this branch: 20261005120000_security_hardening.sql, 20261005150000_resident_record_integrity.sql, 20261005170000_handover_delete_policies.sql and 20261005180000_staff_trainings.sql.
  2. Run the app against local Supabase: npm run dev with the values from .env.test (the Playwright config does this automatically on port 3100).
  3. Test accounts: running any e2e spec (e.g. npx playwright test tests/e2e/journeys.spec.ts) creates two organisations, three care homes, a resident per home and one user per role. Their emails are written to tests/e2e/.auth/world.json; the password for all of them is Test-Password-123!.
  4. For the time-zone bugs (C9, C13, C14, D2–D4, D6) change the computer's time zone to one ahead of the UK (e.g. India) before testing, or test between March and October; everything should still show UK time and the dates you picked.

Running the automated tests

  • Unit: npm run test:unit · Database security: npm run test:db (needs local Supabase)
  • End-to-end: npm run test:e2e; only the resident profile: npx playwright test tests/e2e/resident-
  • HTML report with traces and screenshots of any failure: npx playwright show-report

Manual vs automated testing

The Playwright tests do what a tester does (open pages, click, type, submit) in a real Chrome browser against the real app and local database. They also check the saved data directly in the database, which a manual tester can't easily see. They don't replace a person, because they only check what someone wrote them to check.

Follow-ups and decisions for the team

  • Decide on the open item D13: which care-home fields managers may change (the agency link code needs manager access). D12 is now fixed; confirm the access rule chosen for training records (owners/managers of the care home edit, staff read their own) and whether RQIA inspectors should see them.
  • Apply all four new migrations when deploying: 20261005120000_security_hardening.sql, 20261005150000_resident_record_integrity.sql, 20261005170000_handover_delete_policies.sql and 20261005180000_staff_trainings.sql.
  • Dates saved with toISOString().split("T")[0] remain in about 50 other places. The 47 that compute 'today' are only wrong between midnight and 1 AM UK time in summer; the rest convert a date (care-file assessment dialogs, rota and document date ranges) and should be checked one by one the way D3/D4 were fixed.
  • Handover reports saved before D7 may include duplicates for the same shift; the next save of that shift replaces them all. A one-off clean-up query is optional.
  • Dead code worth deleting: .bak/backup copies of the hospital passport form, the unused comprehensive-incident-form.tsx and report-incident-form.tsx, and components/medication/daily/history-columns.tsx (unused, with the same UTC-time display as D2).
  • Manual testing still matters for what the automated suites cannot judge: layout on tablets/phones, wording and usability, PDF/print output, real email delivery, and production data. See the 'Manual vs automated testing' section.
  • NHS number validation (B16): editing an existing resident whose stored NHS number fails the Modulus 11 check now requires correcting it. Consider a one-off report of residents with invalid numbers.
  • The resident-files storage bucket still accepts any MIME type; only the browser restricts uploads to PDF/images. components/files/UploadFileButton.tsx accepts any file, so restricting the bucket needs checking against that feature first.
  • Pages the page sweep only opens (no deeper flow yet): manager audit (CSV import), appointments and notifications read state, quick-info checks, wounds and medications overviews, agency, MDT summary, settings teams/labels/security.
